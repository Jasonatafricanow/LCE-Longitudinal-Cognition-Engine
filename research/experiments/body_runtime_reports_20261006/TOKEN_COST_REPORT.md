## 3. 成本结构性归因分析

为什么原本旨在“小窗口节约算力”的机械增量，最终导致 Token 严重膨胀？

### 3.1 输入端（Input Tokens）：重复开销叠加（+44.6%）
增量编译并没有减少输入 Token 的总消耗，反而从 24.7k 增加到 35.8k：
1. **系统提示词与协议 Schema 重复投递**:
   MR-Mem 的 Block 编译协议（`BLOCK_COMPILER_PROTOCOL` 包括 JSON schema 约束）约占 2,000 字符。在 5 次独立 API 调用中，该系统前缀被无条件预填充了 5 次。
2. **Lookback 重复滑动重叠**:
   为了避免跨窗口断章取义，每次向前携带 2 条历史原始消息（如 Call 2 读取 6..7，Call 3 读取 14..15 等）。这些长文本证据被重复传输和编码，抵消了窗口切分的截断收益。

### 3.2 输出与推理端（Completion & Reasoning）：灾难级暴增（+943% / +1174%）
输入端仅仅增加了 44.6%，而**输出端与推理端暴增超过 10 倍**，是导致成本彻底失控的绝对主因：
1. **全局压缩压力的消失（Loss of Global Compression Pressure）**:
   - 在 Full-history 一次性编译中，模型面对 34 条长对话（总输入 24.7k），受限于注意力分配与宏观归纳引导，被迫做**高阶事实抽象**，提炼出 3 个核心块、16 个关键谓词（4,280 completion tokens）。
   - 在机械增量的小窗口中（每次仅 8~10 条消息），上下文极为局部。模型在没有全局视野时，会认为“当前窗口内的每一个细节、每个测试名、每个汇报条目都是核心信息”，从而产生**局部的过度忠实与详尽枚举**。
2. **推理预算（Reasoning Tokens）的倍乘效应**:
   - `deepseek-v4-pro` 作为具备深度推理能力的思考模型，其内置的思维链（Reasoning Process）会在每一次生成前进行详尽的边界推演。
   - 单次全量编译中，模型仅思考了一次（2,559 reasoning tokens）。
   - 变成 5 次增量调用后，模型在 Call 1 思考了 8,458 tokens，Call 2 思考了 6,645 tokens，Call 3 思考了 8,333 tokens，Call 4 思考了 5,804 tokens，Call 5 思考了 3,368 tokens。累计思考高达 **32,608 tokens**！
   - 模型在小窗口中反复思考“如何把这几条消息拆得最干净”，反而制造了大量细碎的思维过程。

## 4. 经济性与 API 计费评估

依据 DeepSeek 官方标准定价口径测算：

| 模式 | Input 计费项 (35.8k vs 24.8k) | Completion/Reasoning 计费项 (44.7k vs 4.3k) | 总体 API 资金成本倍率 |
| :---: | :---: | :---: | :---: |
| **Full Pro (Baseline)** | 24,764 tok | 4,280 tok (含 2,559 reasoning) | **1.0x (基准)** |
| **Incremental (增量)** | 35,800 tok | 44,659 tok (含 32,608 reasoning) | **~5.2x (按生成倍率折算)** |

在几乎所有主流大模型 API 定价体系中，Output / Reasoning Token 的单价均显著高于 Input Token（通常为 3~4 倍）。  
因此，增量方案因生成量扩大 10.4 倍、思考量扩大 12.7 倍，其实际财务账单成本不仅没有下降，反而比一次性全量编译**昂贵了 5 倍以上**。

## 5. 结论

```text
INCREMENTAL_RESULT = NO_COST_WIN
```

实验数据以确凿的事实否定了预设假设：  
**“机械切小窗口跑增量编译”在强推理模型（DeepSeek-V4-Pro）下是一个严重的成本负优化策略**。不仅总 Token 激增至 2.77 倍、生成量激增至 10.4 倍，且完全丧失了全历史处理所具备的自发结构归纳与语义压缩能力。
